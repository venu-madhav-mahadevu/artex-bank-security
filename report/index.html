The issues & the fixes

Every weakness, mapped to a defense

Each card: what the weakness is, why it works for an autonomous agent, the code-level fix, and the control that prevents recurrence.

01

No rate limit · no MFA

Critical · credential attacks
In plain words — A vault door that lets anyone try unlimited key combinations as fast as they like, with no guard watching.
Why it works

Login, search and lookup endpoints with no throttle let an agent spray 150k+ attempts and stuff leaked passwords at machine speed.

Fix

Rate-limit per account + IP + device; progressive lockout tuned for bursts, not human pace. Phishing-resistant MFA (passkeys/WebAuthn) everywhere, with step-up on sensitive actions. Screen against breached-password lists; block legacy auth.

Prevent

Alert on login bursts, impossible travel and abnormal records-per-session, especially on partner/employee portals.

How to prevent it — step by step
  • Throttle logins per account, per IP and per device; lock out after a short burst, not after many tries spread over hours.
  • Require phishing-resistant MFA (passkeys / WebAuthn) for everyone, with step-up re-auth before payments, beneficiary changes and limit changes.
  • Screen passwords against known-breached lists and block reuse.
  • Disable legacy / basic auth protocols that skip MFA.
  • Alert on login bursts, impossible travel and abnormal records-per-session — on partner and employee portals too.
02

SQL injection

Critical · data access
In plain words — Scribbling extra instructions on a restaurant order slip that the kitchen blindly carries out.
Why it works

String-concatenated queries let an agent dump credentials and read sensitive tables; error-based SQLi gives it feedback to iterate.

Fix

Parameterised queries / prepared statements everywhere; never concatenate input into SQL. Validate and allow-list input. Run the app on a least-privilege database account.

Prevent

SAST/DAST in CI, a WAF in front, and generic error messages so no stack trace leaks to the attacker.

How to prevent it — step by step
  • Use parameterised queries / prepared statements everywhere; never build SQL by joining strings.
  • Prefer an ORM with bound parameters, and review any remaining raw SQL by hand.
  • Validate and allow-list input (type, length, format) as a second layer.
  • Run the app on a least-privilege database account — no admin or schema rights.
  • Add SAST/DAST in CI and a WAF; return generic errors so no stack trace leaks.
03

Authentication bypass

Critical · identity
In plain words — A bouncer who waves you in on a handwritten “VIP” note without checking whether it’s real.
Why it works

Unsigned/forged SAML assertions and trusted client headers (e.g. an isCliRequest bypass) let an agent walk past login entirely.

Fix

Validate the SAML signature before trusting any assertion; reject unsigned assertions and pin the IdP certificate. Never trust client-supplied headers for auth decisions; centralise authentication.

Prevent

Negative tests with tampered tokens and assertions in CI; fail closed on any validation error.

How to prevent it — step by step
  • Validate the assertion signature before trusting any claim; reject unsigned or wrongly-signed tokens.
  • Pin the IdP certificate and check audience, recipient and the not-before / not-after window.
  • Stop replay with a one-time-use assertion-ID cache.
  • Never trust client headers (isAdmin, isCliRequest, etc.) for authorization decisions.
  • Centralise authentication and add negative tests with tampered tokens in CI.
04

IDOR / broken object authz

Critical · authorization
In plain words — A hotel where changing the room number on your key card opens someone else’s room.
Why it works

APIs that check login but not ownership let an agent enumerate other users' records by changing an ID — ideal for automated harvesting.

Fix

Enforce object-level authorization on every request: confirm the caller may access that specific object. Deny by default; use unguessable identifiers; centralise the check, don't scatter it.

Prevent

Per-endpoint authorization tests; monitor for sequential-ID access patterns.

How to prevent it — step by step
  • Check object ownership on every request — confirm the caller may access that specific record, in the handler.
  • Deny by default, and return 404 not 403 so you don't even confirm the object exists.
  • Use unguessable IDs (UUIDs) instead of sequential numbers.
  • Centralise the check so it can't be forgotten on a new endpoint.
  • Add per-endpoint authorization tests and alert on sequential-ID access patterns.
05

SSRF & XXE → cloud metadata

Critical · cloud takeover
In plain words — Tricking the office mailroom into fetching and handing over the CEO’s private mail.
Why it works

URL-fetch and XML parsers that reach internal addresses let an agent pull cloud instance credentials from the metadata service.

Fix

Allow-list outbound destinations; block link-local and metadata IP ranges. Require IMDSv2. Disable external entities in every XML parser.

Prevent

Egress filtering and network segmentation so a fetch can't reach the control plane.

How to prevent it — step by step
  • Allow-list the exact outbound hosts the app may call; block link-local (169.254.0.0/16) and internal (RFC1918) ranges.
  • Re-resolve and re-check the IP per request to defeat DNS rebinding, and disable or re-validate redirects.
  • Require IMDSv2 (token-based metadata) on cloud instances.
  • Disable DTDs and external entities in every XML parser.
  • Add egress filtering and segmentation so a fetch can't reach the cloud control plane.
06

Unrestricted file upload

High · remote code exec
In plain words — Mailing in a “photo” that is actually a remote control for the whole building.
Why it works

Anonymous uploads with no validation let an agent drop a web shell and run commands on the server.

Fix

Validate type and size, store files outside the web root with random names, disable execution in upload paths, scan on receipt, and serve downloads from a separate domain.

Prevent

Content-type and magic-byte checks; no user-controlled paths; monitor new executable files in served directories.

How to prevent it — step by step
  • Verify the real file type by magic bytes, not the filename or the client-sent type; enforce a size limit.
  • Store uploads outside the web root with random names and no execute permission.
  • Serve downloads through a handler from a separate domain that runs nothing.
  • Scan files with anti-malware on receipt; quarantine first.
  • Never use user-controlled paths; watch for new executable files in served folders.
07

Secrets in code, JS & repos

Critical · the fastest way in
In plain words — Taping the safe’s combination to the front door.
Why it works

API keys in client JavaScript, source maps, .env files and public repos are harvested in minutes — one case went from a GitHub search to key-vault exfiltration in 5 minutes.

Fix

Move secrets to a vault; issue short-lived, rotatable credentials. Strip secrets from client bundles and source maps. Add CI secret-scanning and pre-commit hooks that block pushes containing keys.

Prevent

Rotate immediately on any exposure; monitor public repos and paste sites for your key patterns.

How to prevent it — step by step
  • Keep every secret in a vault and inject at runtime — never in code, .env files, client JS or source maps.
  • Use short-lived, workload-bound credentials (managed identities) and rotate regularly.
  • Add CI secret-scanning and pre-commit hooks that block any push containing a key.
  • Rotate immediately on any suspected exposure and revoke the old key.
  • Monitor public repos and paste sites for your key patterns.
08

Exposed admin / debug & weak sessions

High · surface exposure
In plain words — Leaving the staff-only back door unlocked with the factory “0000” code.
Why it works

Forgotten admin pages, live debug routes, uninitialised installs and guessable session tokens give an agent a quiet way in.

Fix

Remove debug routes in production; gate admin behind auth + MFA + IP allow-list. Harden sessions: strong random tokens, short expiry, rotate on login, HttpOnly/Secure/SameSite cookies.

Prevent

Keep an inventory of every internet-facing surface, including peripheral partner, employee and mobile-backend apps; close uninitialised installs.

How to prevent it — step by step
  • Remove debug / actuator / console routes in production; keep admin internal or behind SSO + MFA + IP allow-list.
  • Change every default credential before first deploy and close uninitialised installs.
  • Use strong random session tokens, short idle expiry, and rotate the session at login and privilege change.
  • Set HttpOnly, Secure, SameSite cookies (prefer the __Host- prefix).
  • Keep an inventory of every internet-facing surface, including peripheral partner, employee and mobile-backend apps.
09

Payment / disbursement API abuse

Critical · fund transfer
In plain words — A cashier who hands out cash the moment you say “withdraw,” skipping every ID check.
Why it works

Disbursal APIs invoked from whitelisted infrastructure can skip loan-creation, KYC, sanction, beneficiary, balance and limit checks when those sit only in the application layer.

Fix

Enforce a server-side state machine: no disbursal until each prior check passes. Add maker-checker (dual approval) for fund movement. Don't treat a whitelisted source IP as authorization.

Prevent

Detect small "test" transactions and abnormal disbursal patterns; re-check scope after any incomplete remediation.

How to prevent it — step by step
  • Enforce a server-side state machine: no disbursal until creation → KYC → sanction → beneficiary → balance → limit checks all pass.
  • Require maker-checker (two-person) approval for fund movement — the maker can't execute their own payout.
  • Verify the beneficiary (penny-drop) and enforce per-transaction and daily ceilings.
  • Don't treat a whitelisted source IP as authorization; re-check in the API layer.
  • Add idempotency keys and flag small “test” transactions before a large one.
10

Over-privileged vendor OAuth apps

Critical · supply chain
In plain words — A trusted contractor’s master key gets copied — no alarm, and every door opens.
Why it works

Trusted multi-tenant apps with broad consent let an agent authenticate as the app — no user sign-in, no MFA prompt — and add credentials for lasting persistence.

Fix

Grant third-party and OAuth apps least privilege; review and scope existing consents. Connect partners through scoped APIs, never shared passwords. Alert when app credentials are added or changed.

Prevent

Monitor service-principal sign-ins and conditional access for app identities; revoke dormant grants.

How to prevent it — step by step
  • Review every OAuth / third-party consent; grant least privilege and scope tokens narrowly.
  • Connect partners through scoped APIs, never shared passwords.
  • Alert when app credentials or role grants are added or changed, and monitor service-principal sign-ins across tenants.
  • Apply conditional access to app identities and revoke dormant grants.
  • Keep an inventory of trusted multi-tenant apps and their permissions.
11

Deepfake liveness bypass

High · identity verification
In plain words — Holding up a lifelike photo to fool a face scanner.
Why it works

Agents try real-time deepfake video and forged ID photos, and reverse-engineer a vendor's liveness event stream to spoof the check from the client side.

Fix

Reach the liveness verdict server-side — never trust the client's event stream. Use randomised challenges, device and metadata integrity checks, and combine passive with active liveness.

Prevent

Flag synthetic camera metadata and parallel verification sessions. (In the one primary record, every attempt was rejected — keep it that way.)

How to prevent it — step by step
  • Compute the liveness verdict server-side — never trust a client “passed” flag or event stream.
  • Use randomised movement challenges and depth / 3D checks; combine passive and active liveness.
  • Verify device and app integrity (Play Integrity / App Attest) and detect virtual cameras and hooking frameworks.
  • Flag synthetic camera metadata and parallel verification sessions.
  • Audit recovery-session API keys and re-verify identity on high-risk actions.
12

No machine-speed detection

High · the meta-issue
In plain words — A night guard who reviews the logs once a day while a burglar works in seconds.
Why it works

Controls tuned to human pace miss an agent that probes permissions, enumerates and pivots in seconds, inheriting sessions a human already authenticated.

Fix

Add behavioural detection for identity-velocity anomalies, API bursts, permission-probing and dry-run capability checks. Distinguish who decided from who logged in; require explicit human confirmation for irreversible actions.

Prevent

Baseline normal volume per identity and alert on deviation; put internal and treasury apps behind Zero Trust access.

How to prevent it — step by step
  • Baseline normal volume per identity and alert on API bursts, enumeration and sub-second permission probing.
  • Distinguish “who decided” from “who logged in”; require explicit human confirmation for irreversible actions.
  • Put internal and treasury apps behind Zero Trust access.
  • Automate containment (disable the identity, revoke tokens) on agent-velocity anomalies.
  • Feed detections to the SOC with burst-aware thresholds.

Catch it in motion

Detection signals for an autonomous agent

  • Login bursts measured in seconds, not minutes; mass lockouts
  • Sequential or enumerating access to records / object IDs
  • Sub-second permission and capability probing (dry-run calls)
  • New app or OAuth credentials added to existing identities
  • Service-principal sign-ins from new IPs across many tenants
  • Outbound traffic to rotating webhook / paste endpoints
  • Abnormal records-per-session on partner and employee portals
  • Small "test" transactions ahead of a larger disbursal
