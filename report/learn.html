Chapter 1

Understanding ARTEX

What the tool is, what it can do, and how security engineers use it legitimately.

1.1How can real engineers use ARTEX?

  • Run authorized penetration tests against systems they own or are cleared to testExample: the security team runs it against the staging banking app before a release
  • Automate repetitive recon and vulnerability probing that would take a human team daysExample: 200 endpoints probed overnight instead of a tester checking each by hand
  • Validate fixes by re-running tests after remediation to confirm a weakness is closedExample: after patching a SAML bypass, re-run it to confirm unsigned assertions are now rejected
  • Continuously check internet-facing surfaces for new misconfigurationsExample: a weekly scan catches a debug endpoint a deploy accidentally left public
  • Free up security staff to focus on complex, judgment-heavy findingsExample: the tool clears routine checks so analysts dig into the tricky logic flaws
  • Always in a lower/test environment first, with security-team approvalExample: runs against test-bank.internal, never production, with sign-off on file

1.2What is the use of ARTEX?

  • Open-source, AI-driven penetration-testing framework (released July 2026, AGPL-3.0, built in Go)Example: anyone can download it from GitHub and run it on their own lab
  • Simulates how an attacker would probe and chain weaknesses — automaticallyExample: it finds a weak login, then a leaked key, then an open database on its own
  • Finds exploitable gaps before real attackers doExample: it spots an exposed admin page the team forgot, so you close it first
  • Maps an organization's external attack surfaceExample: it lists every internet-facing host, including a forgotten partner portal
  • Supports red-teaming and defensive security reviewsExample: a red team uses it to rehearse a realistic attack on their own org
  • Model-agnostic: works with different LLMs as its reasoning engineExample: you can point it at Claude or GPT as its reasoning ‘brain’

1.3What is the power of ARTEX?

  • Works at machine speed — runs many tests in parallel, far faster than humansExample: 200 login endpoints tested in minutes, not days
  • Lowers the skill floor: attack chains that needed experts can now be automatedExample: a junior analyst runs a full chain that used to need a senior pen-tester
  • Chains multiple small weaknesses into one serious compromiseExample: weak login + leaked key + open database combined into one breach path
  • Operates with little human supervision once pointed at a targetExample: set the goal ‘find exposed admin pages,’ walk away, return to a report
  • Adapts its next step based on what it finds (agentic reasoning)Example: finding a config file, it decides on its own to try the database password inside it
  • Scales across many targets at onceExample: it checks dozens of apps in one run instead of one at a time

1.4What vulnerabilities does ARTEX find?

  • Weak or default credentials, missing MFA, no rate limiting on loginsExample: an admin account still on admin / admin
  • SQL injection and other injection flawsExample: a search box where ' OR '1'='1 dumps the users table
  • Authentication / SAML bypassExample: a login that trusts an unsigned SAML assertion
  • IDOR — reaching other users' records by changing an IDExample: changing /invoice/1001 to /invoice/1002 shows someone else's invoice
  • SSRF and XXE — reaching internal or cloud metadata servicesExample: a ‘fetch URL’ feature tricked into reading the cloud metadata service
  • Insecure file upload (web-shell risk)Example: uploading shell.php as a ‘profile photo’ that the server runs
  • Secrets left in code, JS bundles, or public reposExample: an API key committed in config.js on GitHub
  • Exposed admin/debug pages and weak session cookiesExample: /actuator reachable from the internet
  • Payment / disbursement API abuseExample: calling /disburse directly, skipping the approval step
  • Over-privileged vendor OAuth appsExample: a vendor app granted tenant-wide admin
  • Deepfake / liveness-check bypassExample: a deepfake video passed to a liveness check that trusts a client flag
  • Gaps in machine-speed detection and responseExample: 150,000 logins in minutes that no alert flags
Chapter 2

How attackers abuse ARTEX

The same power in the wrong hands — awareness only, so we know what to defend against.

2.1What are hackers doing with ARTEX?

Scanning & attacking at scale, without authorization
Practical example & how to defend

PracticalAn attacker feeds your IP range to the tool. Overnight it maps bank.com, careers.bank.com, an old test-api.bank.com and a vendor portal, and probes them all — ignoring the hardened main app and zeroing in on the forgotten test API running an outdated framework.

Why it’s dangerousYour attack surface is every internet-facing host, not just the flagship app. One forgotten box is enough.

How to defendKeep a live inventory of internet-facing systems; re-scan regularly; retire or VPN/SSO-gate test & legacy systems.

Automating break-ins that used to need experts
Practical example & how to defend

PracticalNo human drives it. It sprays Autumn2026! across logins, lands in a junior staffer’s account, discovers an exposed /admin page, and uses a default admin password to take over — all in one unattended run.

Why it’s dangerousIt lowers the skill floor and runs at machine speed; attacks that needed an expert are now push-button.

How to defendMFA + rate limiting on every login; never expose admin/debug pages; least privilege so one account can’t do much.

Harvesting credentials & secrets, then reusing them
Practical example & how to defend

PracticalThe tool scrapes your public GitHub repo and your site’s JavaScript, finds an AWS_SECRET_KEY a developer left in, and within minutes lists your cloud storage and downloads a database backup. No password was ever guessed.

Why it’s dangerousA valid key means the attacker logs in normally — your firewall/WAF see nothing wrong.

How to defendSecrets only in a vault, never in code; scan repos/JS/CI with gitleaks; on exposure, revoke + rotate immediately.

Hitting many organizations in parallel
Practical example & how to defend

PracticalInstead of one target, it runs the same playbook against 500 companies overnight, grades each (easy/medium/hard), and hands the operator a list of the quick wins to cash in.

Why it’s dangerousScale costs the attacker almost nothing; “we’re too small to be a target” is false — automation hits everyone.

How to defendAssume you’re in scope; get the basics right (MFA, patching, secret hygiene) because automated sweeps don’t skip small orgs.

Chaining known, unpatched weaknesses into a full compromise
Practical example & how to defend

PracticalKorean banks — SQL injection on a peripheral partner system pulled credentials, an auth bypass reached further, and ~67,000 records were exposed. Each flaw alone was “medium”; chained, they became a breach. No zero-day.

Why it’s dangerous“Medium” issues you deprioritize can combine into a full compromise.

How to defendDon’t ignore medium findings; defense-in-depth; protect peripheral/partner systems like the core.

Feeding stolen AI/cloud keys back in to power the next round
Practical example & how to defend

PracticalIt steals a startup’s OpenAI and AWS keys from a leaked config, uses the OpenAI key to run its own reasoning and the AWS key to spin up 50 servers that attack the next 500 targets. The victim’s first clue is a $40,000 bill.

Why it’s dangerousThe attack funds itself with your resources, looks like legitimate usage, and scales for free.

How to defendVault + short-lived, least-privilege keys; spend/usage alerts and hard limits; secret scanning; revoke on exposure; IP allow-list.

2.2How are hackers doing it?

Discovery — scan the internet for exposed apps
Practical example & how to defend

PracticalA mass scan finds an unauthenticated /admin or /actuator endpoint you forgot was public.

Why it’s dangerousYou can’t defend what you don’t know is exposed.

How to defendShrink the exposed surface; alert on scanning patterns; close or gate stray endpoints.

Fingerprinting — identify the product/version
Practical example & how to defend

PracticalIt reads version banners and response headers to match your software to a public CVE (known bug).

Why it’s dangerousKnowing your exact version lets it pick an exploit that already works.

How to defendHide version info; patch quickly so known CVEs can’t be used.

Exploitation — default creds + known flaws
Practical example & how to defend

PracticalConnectWise/Storm-0940: a password spray, then abusing over-privileged OAuth apps to sign in as the app (no MFA prompt).

Why it’s dangerousValid-looking logins and trusted apps slip past perimeter tools.

How to defendMFA everywhere; remove default credentials; least-privilege OAuth app scopes; alert on new app credentials.

Extraction — pull secrets, keys and data
Practical example & how to defend

PracticalA cloud key vault emptied in ~5 minutes once inside.

Why it’s dangerousOnce in, the valuable data goes fast — faster than human review.

How to defendAlert on bulk secret/data access; encrypt; least-privilege data access.

Pivoting — reach connected systems
Practical example & how to defend

PracticalStolen app credentials used across 2,250+ tenants from one foothold.

Why it’s dangerousOne weak spot becomes access to everything connected to it.

How to defendSegment networks; monitor service-principal sign-ins; limit trust between systems.

Speed & scale — all in parallel, machine speed
Practical example & how to defend

Practical150,000+ login attempts in minutes — done before anyone wakes up.

Why it’s dangerousHuman-paced monitoring misses second-scale attacks.

How to defendMachine-speed detection on bursts/enumeration + automated containment.

★Walk-through: how one breach actually unfolds

Setup: The bank has a firewall, a WAF, MFA on the main banking app, and a 24/7 SOC — it feels well covered. But a partner portal, vendor-invoices.bank.com, was spun up two years ago by another team. It sits outside the main WAF, MFA was never enforced on it, and it runs an old library. Everyone forgot about it.

  1. Discover — the tool scans the internet overnight and finds that forgotten portal among thousands of exposed systems.
  2. Credential spray — it tries one common password (Autumn2026!) once against every user. No account hits a lockout, no MFA — and a reused password gives a valid login. The firewall sees a normal, successful sign-in.
  3. Explore — inside, it finds a config file with a database password left in the code.
  4. Extract — it uses that to query a shared database and pulls ~67,000 customer records. The WAF never sees this — it's an internal call, not web traffic.
  5. Speed — the whole thing takes ~15 minutes at 3 a.m. The SOC reviews logs at 9 a.m. By then the data is gone.

Every security system “worked” — but none covered this path:

  • Firewall / WAF → protected the main app, not the forgotten portal
  • MFA → enforced on banking, not on the partner portal
  • The login was valid (reused password) → nothing to block
  • The data pull was internal → invisible to the WAF
  • The SOC was human-speed → the attack was machine-speed

Lesson: no zero-day was needed — just preventable gaps chained fast. Cover every edge, enforce MFA everywhere, vault every secret, and detect at machine speed — the firewall alone is only layer one.

Defensive reference only. Use ARTEX strictly on systems you own or are authorized to test. To close these gaps, see the Fixes and Check-your-code pages.
