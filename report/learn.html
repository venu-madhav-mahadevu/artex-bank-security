Chapter 1

Understanding ARTEX

What this tool is, and how security teams use it the right way.

1.1How do security teams use it?

  • Test their own systems for weak spots — before attackers find themLike this: they run it on the test copy of the bank app before a new release goes live
  • Let the tool do the slow, boring checking by itselfLike this: it checks 200 pages overnight instead of a person doing them one by one
  • Check again after a fix, to be sure the hole is really closedLike this: after fixing a login problem, they run it again to confirm it's gone
  • Keep an eye on which systems are open to the internetLike this: a weekly check finds a page a new release accidentally left open
  • Free up the security team for the harder problemsLike this: the tool handles the routine checks; people focus on the tricky ones
  • Only on systems they're allowed to test, in a safe test setup, with the boss's approvalLike this: they test a copy, never the live site, and get sign-off first

1.2What is it for?

  • A free, open tool that uses AI to test securityLike this: anyone can download it and run it on their own practice systems
  • It acts like a hacker would — but to help you find problems firstLike this: it finds a weak login, a leaked key, and an open database on its own
  • It finds weak spots before real attackers doLike this: it spots a forgotten admin page so you can close it in time
  • It shows which parts of your systems are open to the internetLike this: it lists every public system, including a forgotten partner site
  • It lets security teams practice real attacks safelyLike this: a team uses it to rehearse an attack on their own systems
  • It can use different AI ‘brains’Like this: you can point it at a Claude- or ChatGPT-style model

1.3What makes it powerful?

  • It works very fast — many checks at the same timeLike this: it tests 200 logins in minutes, not days
  • It makes hard attacks easy — what needed an expert, anyone can run nowLike this: a brand-new team member runs a full attack the tool works out
  • It joins small problems into one big break-inLike this: weak login + leaked key + open database together become a full breach
  • It mostly runs on its own once startedLike this: you say ‘find open admin pages,’ walk away, and come back to a report
  • It decides its next move based on what it findsLike this: it finds a settings file and decides on its own to try the password inside it
  • It can go after many systems at onceLike this: it checks dozens of apps in a single run

1.4What weak spots does it find?

  • Weak or default passwords, and logins with no second step (MFA)Like this: an admin account still using ‘admin / admin’
  • Tricking the database with bad input (SQL injection)Like this: typing special text in a search box to pull out every user
  • Logins that trust the wrong thing (authentication / SAML bypass)Like this: a login that accepts a fake, unsigned pass
  • Seeing other people's data by changing a number (IDOR)Like this: changing invoice 1001 to 1002 shows someone else's invoice
  • Tricking a system into fetching private internal data (SSRF/XXE)Like this: a ‘load this link’ feature made to read secret internal info
  • Unsafe file uploads that run code (web shell)Like this: uploading a harmful file disguised as a photo, which the server then runs
  • Passwords or keys left inside the code (hardcoded secrets)Like this: a secret key accidentally posted on GitHub
  • Forgotten admin or test pages left open (exposed admin / debug endpoints)Like this: an internal control page anyone on the internet can reach
  • Weak checks on money transfers (payment / disbursement API abuse)Like this: a money-sending feature that skips the approval step
  • Outside apps given too much access (over-privileged OAuth apps)Like this: a connected vendor app allowed to do almost anything
  • Fake faces fooling identity checks (deepfakes)Like this: a fake video passed to a face-check that trusts the user's own device
  • No fast alarms when an attack is happening (no machine-speed detection)Like this: 150,000 login tries in minutes and nothing raises an alert
Chapter 2

How attackers misuse it

The same power in the wrong hands — shown only so we know what to protect against. Remember: using it with permission on your own systems is security work; using it without permission on others is a crime.

2.1What are attackers doing with it?

Attacking lots of systems at once, without permission
A real example & how to protect

Examplean attacker points the tool at all of a bank's web addresses. Overnight it finds not just the main site but old, forgotten ones — and attacks those.

Why it's riskyevery system open to the internet is a possible way in, not just the main one. One forgotten site is enough.

How to protectkeep a list of all your public systems, check them often, and shut down or lock away old/test ones.

Doing expert-level break-ins automatically
A real example & how to protect

Exampleno person is needed. It tries a common password on many accounts, gets into one, finds an open admin page, and takes over — all by itself.

Why it's riskyattacks that used to need a skilled person now run on their own, very fast.

How to protectadd a second login step (MFA) everywhere, limit how many login tries are allowed, and don't leave admin pages open.

Stealing passwords and keys, then reusing them
A real example & how to protect

Exampleit finds a secret key a developer left in public code and, within minutes, uses it to open the company's cloud storage and download a backup.

Why it's riskywith a real key, the attacker just logs in normally — your firewall sees nothing wrong.

How to protectnever put keys in code (keep them in a secure vault), scan your code for leaks (e.g. gitleaks in CI), and cancel + replace any key that leaks.

Hitting many companies at the same time
A real example & how to protect

Exampleinstead of one bank, it runs the same attack on 500 companies in a single night and reports the easy wins.

Why it's riskygoing big costs the attacker almost nothing. ‘We're too small to be a target’ is not true.

How to protectassume you could be targeted and get the basics right: MFA, updates, and no leaked keys.

Joining small weaknesses into a big break-in
A real example & how to protect

Exampleat the Korean banks, a few ‘small’ problems on a side system were linked together and about 67,000 people's data was exposed. No brand-new trick was used.

Why it's riskysmall problems you keep putting off can add up to a real breach.

How to protectfix the ‘small’ problems too, use several layers of defense, and protect side systems like the main one.

Using stolen AI/cloud keys to power more attacks
A real example & how to protect

Exampleit steals a company's AI and cloud keys and uses them to run its own attacks on the next targets — the victim even pays the bill.

Why it's riskythe attack pays for itself using your resources, and it looks like normal usage.

How to protectkeep keys in a secrets vault, make them short-lived, watch your usage/bills for sudden spikes, and cancel leaked keys right away.

2.2How do they do it, step by step?

Find — look across the internet for open systems
A real example & how to protect

Examplethey scan and find a control page that has no login.

Why it's riskyyou can't protect something you didn't know was open.

How to protectreduce what's open to the internet, and watch for scanning.

Identify — work out what software you run
A real example & how to protect

Examplethey read small clues to learn your software and version, then pick a known weakness for it.

Why it's riskyknowing your exact version lets them choose an attack that already works.

How to protecthide version details, and keep your software updated.

Break in — try default passwords and known holes
A real example & how to protect

ExampleConnectWise case: they guessed passwords, then misused a trusted connected app (an over-privileged OAuth app / service principal) to sign in as the app, skipping the user's MFA.

Why it's riskynormal-looking logins and trusted apps slip past your usual defenses.

How to protectMFA everywhere, remove default passwords, and limit what connected apps can do.

Steal — grab keys and data once inside
A real example & how to protect

Examplea store of secret keys was emptied in about 5 minutes.

Why it's riskyonce in, the valuable stuff goes fast — faster than people can react.

How to protectset alarms for large or unusual data grabs.

Spread — use what they found to reach more
A real example & how to protect

Examplestolen app access reached 2,250+ companies from one starting point.

Why it's riskyone weak spot can open the door to everything connected to it.

How to protectkeep systems separated, and watch connected-app logins.

Speed — do it all at once, very fast
A real example & how to protect

Example150,000 login tries in minutes — finished before anyone wakes up.

Why it's riskychecking logs once a day is far too slow for this.

How to protectuse fast, automatic alarms that can shut things off on their own.

★A simple story: how one break-in happens

The setup: the bank has a firewall and web application firewall (WAF), a second-step login (MFA) on the main app, and a security operations team (SOC) watching around the clock — it feels safe. But two years ago another team put up a small partner website, vendor-invoices.bank.com. It sits outside the firewall, has no MFA, and runs old software. Everyone forgot about it.

  1. Find — an overnight scan spots that forgotten website among thousands.
  2. Guess a password — it tries one common password on each user. No account locks, no MFA — and one person had reused that password, so it gets a real login. The firewall sees a normal sign-in.
  3. Look around — inside, it finds a settings file with a database password written right in it.
  4. Take the data — it uses that to pull about 67,000 customer records. The firewall never sees this — it's an internal request, not web traffic.
  5. Too fast — the whole thing takes about 15 minutes at 3 a.m. The team reads the logs at 9 a.m. By then it's over.

Every security tool “worked” — but none covered this path:

  • The firewall protected the main app, not the forgotten website
  • MFA was on the main app, not on the partner website
  • The login was real (reused password) — nothing to block
  • The data was taken internally — the firewall couldn't see it
  • The team checks at human speed — the attack ran at machine speed

The lesson: no secret, brand-new trick was needed — just everyday problems left open and linked together quickly. Cover every system (not just the main one), use MFA everywhere, keep keys and passwords out of the code, update your software, and use fast automatic alarms. The firewall alone is only the first layer.
